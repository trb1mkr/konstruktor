# 🧱 Блокировка запросов расширениями (declarativeNetRequest): план на будущее

Что уже выяснено замерами и вошло в документацию, здесь не повторяется: механика DNR в Electron рабочая, наборы включаются вызовом `updateEnabledRulesets` (так делает и uBlock Origin Lite), статические правила блокируют запросы подресурсов, а предупреждение на карточке расширения сейчас недостоверно. Детали и замеры — в `src/main/extensions/EXTENSIONS.md`, раздел «Чего в этом Electron нет».

Ниже — только незакрытое.

## 🩹 Этап 1. Достоверное предупреждение вместо ложного

`declaresRequestBlocking` в `manager.ts` ставит на карточку текст «наборы правил блокировки (declarativeNetRequest) не загружаются: блокировка не работает». Это неверно: наборы включаются программно, и у uBlock Origin Lite блокировка запросов подресурсов после этого работает. Варианты замены:

- убрать предупреждение совсем;
- оставить текст только про реальное ограничение — правила DNR не матчатся для переходов верхнего уровня (`main_frame`).

Текст предупреждения собирается при установке, поэтому правка — одна строка в `manager.ts` плюс перезапись текста у уже установленных расширений (иначе старая строка останется в реестре до переустановки).

## 🔧 Этап 2. Автовключение наборов в шиме

Chrome включает наборы правил, объявленные в манифесте с `enabled: true`. Electron — нет, поэтому расширение обязано включить их само вызовом `updateEnabledRulesets`. uBlock Origin Lite это делает, а другое DNR-расширение может и не делать — и тогда его наборы останутся выключенными, хотя причины винить Electron нет.

После подъёма фона расширения, объявившего `declarative_net_request`, шим включает наборы сам:

- список берётся из манифеста (`rule_resources`), а не из `getEnabledRulesets()` — последний уже отфильтрован текущим состоянием;
- включаются только наборы с `enabled: true`;
- идемпотентно, повторный вызов ничего не ломает;
- best-effort в `try/catch` — сбой включения не должен ронять фон;
- только для расширений с `declarative_net_request`, чтобы не трогать остальных.

## 🧪 Этап 3. Отчёт по DNR в автопрогоне

Расширить автопрогон расширений (`KONSTRUKTOR_EXT_SMOKE`) отчётом по DNR: объявленные наборы, включённые наборы, `testMatchOutcome` для пары URL (один подходящий, один безобидный). Нужно, чтобы регрессию было видно без ручного похода на рекламную страницу. Вывод и параметры флага задокументировать в `src/main/docs/DIAGNOSTICS.md`.

## 🧯 Этап 4. Запасной путь (только при доказанной неработоспособности DNR)

Если DNR окажется неприменим по причинам, которых не было в замерах, блокировку поднимает main своим слоем:

- свой разбор наборов расширения (`urlFilter`, `resourceTypes`, домены, приоритеты, действия block/allow/redirect) с индексом по домену и применением через `session.webRequest.onBeforeRequest`;
- либо готовая библиотека `@ghostery/adblocker-electron` (MPL-2.0) поверх тех же списков.

Путь тяжёлый — свой мини-движок или внешняя зависимость, — поэтому берётся только под доказанную неработоспособность механики, а не заранее. Трансляция наборов в динамические правила не годится: у блокировщиков десятки тысяч правил, а лимит динамических — 5000.

## ⚠️ Что учесть при работах

- Правила DNR не матчатся для `main_frame`: блокировка переходов верхнего уровня требует отдельной проверки и, возможно, отдельного решения.
- Наборы кэшируются Chromium: правка файлов правил без смены идентификатора набора не подхватывается (замерено — старое содержимое продолжало матчиться).
