# 🔧 Troubleshooting

Документ собирает нюансы сборки, окружения и инструментов, которым не нашлось места в профильных документах.

## 🛠️ Сборка, окружение и инструменты

Модульная система, ESM/CJS-прелоады, sandbox и средства отладки.

### 📦 ESM-прелоад и sandbox

При `"type": "module"` прелоад собирается в `.mjs`/`.cjs`: нужен `sandbox: false`, иначе `window.browserAPI` молча `undefined`. CJS-билд лежит рядом (`index.cjs`).

### 🛠️ Правки кириллицы в редакторе

Многострочные правки с русским текстом через `replace_string_in_file` способны слить строки или потерять переводы строк. Надёжный способ — одноразовый `patch*.cjs` с заменами и запуск через `node`; inline-код в PowerShell калечит кавычки.

### 🔦 Логи renderer не доходят до терминала

`ELECTRON_ENABLE_LOGGING=1` отдаёт console-сообщения оболочки выборочно: строки вида `[i18n] init lang=en` из shell периодически не появляются в stdout, и картина выглядит так, будто renderer-код не выполнялся. Логи shell читаются через DevTools окна; для проверки путей main ↔ shell работает временный IPC-канал, дублирующий сообщения в консоль main — вывод main-процесса стабилен. Отсутствие строки при живом приложении — признак пропущенного вывода, а не пропущенного выполнения.

### 🧩 Обновление зависимостей ломает запуск: два характерных симптома

После обновления пакетов (i18n, Electron) `npm run dev` падает на старом `node_modules`:

1. `Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'i18next' imported from out/main/index.js` — в `node_modules` нет нового пакета, `npm install` не прошёл или прошёл частично. Проверка: `ls node_modules/i18next`. Лечение — полный `npm install` (не точечная установка), затем сверка `package-lock.json`.
2. `Error: Electron uninstall` из `electron-vite` при собранном билде — пакет `electron` на месте, но не скачан дистрибутив: нет `node_modules/electron/dist` и `path.txt` (с Electron 42 у пакета больше нет своего `postinstall`, а `electron-vite` читает `path.txt` сам и докачку не зовёт). Дистрибутив качает хук `postinstall` из `package.json`; ошибка значит, что хук пропущен (`ignore-scripts`, обрыв сети, установка из кэша). Лечение: `node node_modules/electron/install.js`, после чего появляются `path.txt` и `dist/`.

Сборка (`out/`) при этих ошибках успевает пройти — падает только старт Electron, поэтому симптомы выглядят как «приложение не запускается», а не «билд не собирается».

## 🌐 Внутренние страницы, i18n и меню

### 🏷️ Пустые подписи, посчитанные на уровне модуля

Строка, вычисленная `t()` (`main/i18n.ts`) в теле модуля, приходит пустой: i18next до `initI18n()` отдаёт `undefined`, а импорт модуля случается раньше инициализации. Симптом — в таблице горячих клавиш `konstruktor://settings` колонка «действие» была пустой (без ошибок в консоли). Лечение: резолвить строки внутри `build*Page()` — страница собирается на запрос, уже после `initI18n()` (в `settingsPage.ts` это `hotkeyLabels()`) — или в момент показа меню, как у пунктов контекстного меню. Проверка: `node -e "console.log(require('i18next').default.t('hotkeys.actions.reload'))"` печатает `undefined`.

### ⌨️ `preventDefault` в `before-input-event` убивает `keydown` страницы

`event.preventDefault()` в `before-input-event` гасит не только акселераторы дефолтного меню Electron, но и `keydown`/`keyup` самой страницы — нажатие до неё не доходит. Поэтому гасить акселераторы безусловно нельзя там, где ввод нужен странице: в таблице горячих клавиш (`konstruktor://settings`) поле в фокусе не получило бы нажатия вовсе, и сочетание не набралось бы. Вариант с «погасить всё, но ничего не делать» не работает.

Лечение: `webContents.setIgnoreMenuShortcuts(true)` на время фокуса в поле — он снимает только акселераторы меню, `keydown` доходит до страницы. Реализация — `main/hotkeys.ts` (`setHotkeyCapture`/`isHotkeyCapture`), см. [TABS.md](../src/main/tabs/TABS.md) «Захват сочетаний».

### 🖼️ Класс `.row` из shell внутри диалога

`.row` в `shell.ts` — строка списка истории/загрузок: фон, рамка, отступы, `:hover`. Внутри `<dialog>` она читается как чужеродная растянутая обводка вокруг кнопок: локальное правило вида `dialog .row { display: flex; justify-content: flex-end }` перебивает только раскладку, а фон, рамку и отступы оставляет. Симптом — широкая рамка на всю ширину диалога с кнопкой у правого края.

Лечение: у ряда кнопок свой класс (`dialog .dlg-actions` на стартовой, `dialog.hk-dialog .hk-dialog-actions` в настройках), `.row` остаётся строкам списков. Размер кнопки диалога — как у диалога иконки вкладки (`DialogForm.vue`: `padding: 6px 12px`, `font-size: 13px`).

## 🎨 Темы

Грабли темизации веб-контента.

### 🌓 Тема браузера не применяется к сайтам и окнам расширений

Симптом: тема интерфейса тёмная или `slate`, а Google, Wikipedia и попапы расширений остаются светлыми.

Причина была в способе применения. `insertCSS` с `:root { color-scheme: dark }` предпочтения документа не переключает: свойство `color-scheme` меняет только used-схему UA-виджетов и наследование в iframe/SVG, а результат `prefers-color-scheme` остается от темы ОС. Сайты, выбирающие палитру по медиазапросу, видели мнение ОС, а не браузера. Окна попапов расширений в цикл применения не попадали вообще: `applyThemeToViews` ходит по view вкладок, а попап стартовал с белым фоном по умолчанию.

Лечение: схему веб-контента задает `nativeTheme.themeSource` — он переключает `prefers-color-scheme` во всех webContents, включая уже загруженные. Ставится в `applyWebContentScheme` при старте (до первого окна) и на смене темы; окно попапа получает `backgroundColor` из `webContentBackground()`. Проверка: `THEME_DEBUG=1 npm run dev` при тёмной теме ОС и теме браузера `dark` — в логе `[theme] web content: browser=dark override=follow -> dark`, а на сайте со `prefers-color-scheme` (Wikipedia, MDN) страница тёмная.

Сайты с захардкоженными цветами и `color-scheme: only light` не изменятся ничем: их палитра не зависит от браузера.

### 🌚 Светлый ползунок и «тема не сразу»

Симптомы: при тёмной теме браузера полоса прокрутки остаётся светлой, а смена базовой темы видна только после нескольких перезагрузок страницы.

Причина: тема ставилась только через `themeSource`. `prefers-color-scheme` от него доезжает до renderer асинхронно, а used-схему (цвет ползунка, форм, канвас) вообще не меняет: ползунок берет цвет из `color-scheme` документа, а не из медиазапроса. Поэтому скроллбар оставался светлым, а первая перезагрузка могла подхватить ещё старое значение.

Лечение: обе механики вместе. `applyWebContentScheme` (themeSource) плюс инъекция `:root { color-scheme: dark|light !important }` в `applyThemeToTab` — синхронно, при создании вкладки и на каждом `did-finish-load`, с запоминанием ключа в `TabData.themeKey` для снятия предыдущей. Ползунок и виджеты попапа расширения красятся той же инъекцией (`effectiveColorScheme()`). Перезагрузка тогда нужна только сайтам, которые читают тему один раз при загрузке (Google, отдельные SPA) — это их поведение, а не браузера.

## 🗂️ Файлы данных

Грабли записи JSON-хранилищ: история, загрузки, настройки, слепки окон.

### 💥 `history record failed: ENOENT ... history.json.tmp`

Симптом: в логе пачка ошибок `rename '.../history.json.tmp' -> '.../history.json': ENOENT`, история теряет записи. Чаще всего видно после восстановления нескольких вкладок сразу.

Причина: `writeJsonAtomic` писал временный файл с постоянным именем `<файл>.tmp`. История пишется на каждую навигацию, вкладки грузятся параллельно — и две записи берут ОДИН И ТОТ ЖЕ tmp. Первая успевает переименовать его, вторая падает: переименовывать уже нечего.

Лечение: имя временного файла уникально для каждой записи (`<файл>.<pid>-<время>-<hex>.tmp`, `workspaces/atomic.ts`). Оборванная запись оставляет мусор, но он больше никому не мешает. Проверка: восстановить 4–5 вкладок разом и убедиться, что строк с `record failed` в выводе нет.

### ⏱️ Аварийное завершение не предлагает восстановление

Симптом: процесс убили или он упал, а следующий запуск молча открывает вкладки без диалога (либо, наоборот, предлагает восстановление после штатного выхода).

Причина в маркере сессии (`workspaces/sessions.ts`). Маркер `session.lock` пишется синхронно до первого окна и удаляется при штатном выходе. Если его нет на старте — авария не обнаружится; если он не снят после штатного выхода — будет ложное восстановление. Снимается он в двух местах: `before-quit` и закрытие последнего окна пространства.

Отдельная ловушка при проверке: `process.exit(1)` аварию НЕ имитирует — Electron прогоняет закрытие окон, хук `closed` снимает маркер, и сессия записывается штатной. Для имитации используйте `KONSTRUKTOR_CRASH_MS` (внутри — `SIGKILL`).

Проверка: `KONSTRUKTOR_CRASH_MS=5000 npm run dev` (в логе `[diag] simulating crash: SIGKILL`), затем обычный запуск — в логе `[session] previous run did not close`, `[workspace] previous session ended abnormally` и диалог с выбором «Восстановить / Начать заново».

### 🧩 Расширение второго пространства теряет меню и хранилище

Симптом: в первом пространстве расширение работает, а в скопированном (или просто втором открытом) его кнопка не открывает меню, попап падает, собственное хранилище пустое; в логе `Uncaught (in promise) Error: unknown extension`.

Причина: мост расширений один на процесс, а запись искалась только в реестре ПРОСТРАНСТВА ЗАПУСКА (`findExtensionByElectronId` с `bootWorkspaceId()` по умолчанию). `electronId` выдаётся при загрузке в партицию и однозначен в пределах процесса, поэтому ограничение было лишним и работало только пока открыто одно пространство.

Лечение: поиск идёт во всех кэшах реестров (`findExtensionByElectronIdAny`, `findExtensionRecordAny`), а хранилище `konstruktor.storage` адресуется КАТАЛОГОМ расширения (`rec.dir`), а не id в пространстве запуска — иначе данные попали бы в чужое. Проверка: открыть два пространства с одним расширением и убедиться, что в логе нет `unknown extension`, а у каждого пространства свой `konstruktor-storage.json` в каталоге его расширения.
### 🗂️ На странице пространств нет выбора «Копировать настройки из»

Симптом: в форме создания пространства видно только имя, иконку и цвет — селектор источника копирования и флажки секций отсутствуют, скопировать конфигурацию нельзя вовсе.

Причина: `syncCopyBlock` в `pages/workspacesPage.ts` прятал блок `#copy-block` целиком, когда значение селектора — «не копировать». Селектор лежал ВНУТРИ этого блока, поэтому спрятать себя он мог, а показать обратно нечем: у страницы нет другого входа к этому значению.

Лечение: скрывается только подсказка и флажки (`#copy-details`), сам селектор источника виден всегда в режиме создания. Проверка: открыть `konstruktor://workspaces`, нажать «Создать» — селектор «Копировать настройки из» на месте; выбрать существующее пространство — появляются секции.

## 🔐 Разрешения сайтов

Грабли системы разрешений: камера, микрофон, геолокация, уведомления, устройства.

### 🎤 Разрешения выдаются сайтам без спроса

Симптом: Google Meet получает камеру и микрофон сразу, промпта нет, хотя система разрешений в коде есть.

Причина: обработчиков разрешений в сессии нет. Дефолт Electron для `setPermissionRequestHandler` — разрешать запрос, поэтому без явных `setPermissionRequestHandler` и `setPermissionCheckHandler` на сессии `media`, `notifications`, `geolocation` и прочее выдаются молча. Ставит их `permissions/permissionManager.ts` (`initPermissions`), и вызывается это ДО первого окна в `whenReady`: обработчик, поставленный после первой навигации, опоздает — первая вкладка успеет запросить доступ.

Проверка: при старте в логе `[overlay:session  ] permission handlers installed` (terse-режим logger'а видит категорию `session`). Дальше на https-сайте при запросе микрофона должен появиться промпт под адресной строкой; автопрогон — `KONSTRUKTOR_PERM_SMOKE=http://localhost:5173/ npm run dev` (в логе `permission prompt shown`).

### 🔌 Запрос разрешения висит, страница ждёт вечно

Симптом: промпт показался, пользователь закрыл его Escape или кликом по подложке, а `getUserMedia` не отклоняется — страница остаётся в состоянии «запрос идёт», индикатор загрузки не гаснет.

Причина: обработчик разрешения обязан вызвать `callback(...)` ровно один раз на любой исход, включая отказ. Промпт закрывается не только выбором пользователя: Escape, клик по подложке, уход из приложения (Alt+Tab), вытеснение другим оверлеем, прерванный показ. Вложенность уровней оверлея выключена (`NESTED_DIALOGS = false`), и новая поверхность снимает прежнюю через `clearSession` без единого колбэка — то есть о снятии промпта никто бы не узнал.

Лечение: оверлей сообщает о завершении сессии слушателями (`onOverlayEnded` в `overlay/close.ts`), а зовут их все точки закрытия, включая ветку вытеснения в `showOverlay`. Очередь промптов превращает это событие в отказ. При переносе механики закрытия в другое место — не забыть уведомление, иначе повисший запрос вернётся.

Слушателей несколько, а не один: второй потребитель — диалог восстановления после аварии. Одиночный слот отдавал событие только последнему подписавшемуся, и регистрация диалога отключала отказ промпту разрешений.

Проверка: тот же сценарий с `OVERLAY_DEBUG=1 npm run dev` — в логе `permission prompt closed -> denied`, а в консоли страницы `NotAllowedError`. В автопрогоне этот путь проверяет завершение приложения: при выходе промпт снимается и запрос отклоняется (`[perm-smoke] result: DENIED:NotAllowedError`).
